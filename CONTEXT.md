# QRB (Quantum Resource Binder)

Quantum resource selection modeled as QoS-Aware Service Composition (QACO). QRB
maps a quantum task + declared preferences onto the Binding Instance Model (BIM) of the
OpenBinding gateway, which returns the optimal binding of the task to a quantum resource.

## Language

### Domain model (BIM)

**BIM (Binding Instance Model)**:
The formal QACO tuple `(T, P, C, F, G, Λ, Δ, O)` that OpenBinding solves. QRB's job is
to produce a valid BIM instance from a quantum problem.

**Task**:
An abstract computational problem, expressed functionally and independently of any
technology (`T`). In a single-task workflow there is exactly one.
_Avoid_: using "task" to mean the submitted Circuit — the Circuit is one concrete
expression of a Task, not the Task itself.

**Circuit**:
The concrete OpenQASM 3 program the user submits — a functional specification standing in
for the abstract Task. Source of task-dependent Features via Transpilation.

**Provider**:
A platform that offers access to quantum resources (`P`). In scope: IBM Quantum, Amazon
Braket.
_Avoid_: conflating Provider with the hardware vendor (IonQ, Rigetti) — see open question.

**Resource** (Quantum Resource):
A physical gate-based QPU, identified by its hardware — topology, native gate set,
calibration. Holds the hardware-derived data (drives `expected_fidelity`, `num_qubits`).
The catalog is QPU-only (simulators are out of scope).
_Avoid_: "backend", "device" — pick Resource. A Resource is _not_ a Candidate: one Resource
can be offered by several Providers.

**Candidate**:
A concrete way of solving a Task: a Task materialized on a specific Resource **through a
specific Provider** — i.e. an _offering_ (`C`). The unit that gets ranked and bound. Every
Candidate belongs to exactly one Task (`τ:C→T`) and one Provider (`π:C→P`). The same
Resource offered by two Providers yields two Candidates: identical hardware Features
(`expected_fidelity`, `num_qubits`), differing platform Features (`cost`, `queue`).

**Binding**:
A function assigning the Task to one of its Candidates (`b:T→C`). The output of a solve.

**Feature** (QoS Feature):
A quantitative quality attribute of a Candidate (`F`), with a direction (MAXIMIZE/MINIMIZE),
unit, scale, and valid range. Four categories: **static**, **dynamic**, **provider**,
**task-dependent**. Current set: `cost`, `queue`, `expected_fidelity`, plus `num_qubits`
(present but unweighted, anchors feasibility).
_Avoid_: "metric", "attribute" as loose synonyms — a Feature is the formal `F` element.

**Objective**:
The aggregated quality criterion to optimize (`O`) — a weighted trade-off over Features
that selects the optimal feasible Binding. Two modes: **scalarized** (MONO — weights collapse
to a single optimum, one Binding) or **Pareto** (MANY — a set of non-dominated Bindings). The
objective mode selects the default solver Engine.
_Avoid_: "figure of merit" — that is the state-of-the-art term for this same concept;
QRB reinterprets a SOTA figure of merit as a particular Objective instance (e.g. a
pure-fidelity figure of merit = an Objective weighting `expected_fidelity` at 1.0).

**Constraint**:
A hard or soft restriction on a Binding (`Δ`).

**Feasibility Constraint**:
The _mandatory_ hard Constraint capturing circuit–hardware compatibility: qubit capacity,
`num_qubits ≥ circuit width`. Auto-generated by QRB and enforced by the solver, never
authored by the user. The only feasibility QRB imposes automatically — depth feasibility
(NISQ Analyzer's `depth_feasible` bound, salm2020) is a computed Feature instead, available
as an optional user-authored Constraint, not auto-enforced.

**Normalized Feature**:
The `<id>_normalized` companion of an objective-eligible Feature (`expected_fidelity`,
`cost`, `queue`), min-max scaled to [0,1] across the candidate set actually fetched for one
request, direction-aware so higher is always better. The Objective's weights/targets
reference the Normalized Feature; the raw Feature stays untouched for Constraints and
display.

**Aggregation Policy**:
Operators that aggregate Features along the workflow (`Λ`). Reduce to identity for a
single-task workflow.

### QRB concepts

**Preferences**:
A user's declared Objective + Constraints for a single request. The reconfigurable,
per-request data whose expressiveness is the paper's thesis.

**Preset**:
A named, reusable Preferences profile (e.g. `balanced`, `fidelity-first`). Built-in presets
ship with QRB; users may define their own.

**Catalog**:
The set of Candidates available for a solve, drawn live from the Providers.

**Snapshot**:
A recorded Catalog serialized for reproducibility. Live fetch is the default; a snapshot is
opt-in (`--snapshot`).

**Expected Fidelity**:
A task-dependent Feature ∈ [0,1]: the estimated probability the Circuit executes correctly
on a Resource. Computed as an Estimated Success Probability (ESP) over the _compiled_
circuit — `∏ F(gᵢ) · ∏ F_RO(qⱼ)`, the product of per-gate execution fidelities and per-qubit
readout fidelities. `0` (worst score) for Resources too small for the Circuit.

**Transpilation**:
Rewriting a Circuit to a Resource's native gate set and qubit topology. Produces the
task-dependent Features (transpiled depth, 2-qubit gate count, Expected Fidelity).
